# Cantinarr documentation

The public help site at **https://docs.cantinarr.com**. Astro and Starlight provide static pages, local search through Pagefind, keyboard navigation, a mobile menu, light and dark themes, and copyable code examples. Fonts and site assets are served locally. The site has no analytics, accounts, or runtime API.

## Work locally

Use Node 22.12 or newer and Python 3.9 or newer. Run from this directory:

```sh
npm ci
npm run dev
```

For the complete searchable production preview:

```sh
npm run build
npm run preview
```

Pagefind is generated by the production build. The development server explains that search is unavailable until a production build; use the preview when checking search. Astro 7 runs its local server as a background process. Stop it with `npx astro dev stop` or `npx astro preview stop` when finished.

## Content ownership

Task guides live under `src/content/docs/`. The writing guide is [Maintain these docs](src/content/docs/contributing/documentation.md). Sidebar structure lives in `astro.config.mjs`. The documentation map builds itself from the content collection.

`scripts/sync_reference.py` imports the owning files from the same Git checkout:

| Source | Published material |
| --- | --- |
| Root README | Environment variable table |
| Server README | API groups and architecture contracts, including MCP tools |
| App README | Screen behavior and navigation |
| Settings search registry | Complete searchable-settings catalog |
| `docs/*-setup.md` and `docs/apple-tv.md` | Maintained integration instructions |
| Privacy policy and release playbook | Their complete maintained text |

Generated Markdown and its source manifest are ignored by Git. Edit the original file linked at the bottom of an imported page. The importer checks source fingerprints, rewrites relative links, and applies the public punctuation rule. It updates changed files in place so a running development server does not lose the collection during regeneration.

The site follows development main. Every page explains that stable installations may differ and links to version guidance. The footer links to the exact source revision used for that build.

## Verification

`npm run build` synchronizes references, builds every page and the search index, then validates the final HTML. It fails on broken local links or fragments, missing assets, missing metadata, more or fewer than one H1, em dashes in visible text, stale imported sources, missing required topics, undocumented server configuration names, missing MCP tool names, or settings omitted from the live search registry. The environment audit scans production Go files, the container entrypoint, proxy conventions, and both Dockerfiles; build arguments and the explicit provider test override must be classified in the development guide. External availability is checked separately when links change, so an unrelated provider outage cannot block a build.

The `Documentation` job in the repository CI runs this build for every PR and main/release push and uploads the static output as an artifact. Application code is unaffected by the docs build; `docs-site/` is excluded from Docker build contexts.

## Publishing

Cloudflare Pages project: `cantinarr-docs`. Production domain: `docs.cantinarr.com`. Output directory: `docs-site/dist`.

The companion [`cantinarr-site`](https://github.com/windoze95/cantinarr-site) repository owns the `Deploy Docs` workflow because it already owns Cantinarr's Cloudflare deployment credentials. On its schedule or manual dispatch it resolves the current Cantinarr `main` SHA, requires successful `CI` for that exact SHA, skips an already published SHA, checks out that source, and rebuilds with the lockfile before publishing. It never builds an arbitrary user-supplied ref with deployment credentials. The marketing site's existing deployment remains independent.

An authorized maintainer can publish a verified build manually with existing Wrangler authentication:

```sh
npm run build
npx wrangler@4 pages deploy dist --project-name=cantinarr-docs --branch=main --commit-hash="$(git rev-parse HEAD)"
```

Verify the live homepage, a nested guide, search assets, a missing route's 404 response, and security headers after publication. A successful upload alone does not prove the custom domain works.
